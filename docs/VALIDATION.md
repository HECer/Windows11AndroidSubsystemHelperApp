# Validation record — 0.1.0 candidate

Recorded November 6, 2026 on Windows x64 using .NET SDK 10.0.203.

- Release build: succeeds with warnings treated as errors.
- Core regression suite: 60 cases cover download integrity and cache replacement, malformed/traversing/link archives, journal recovery, package/endpoint validation, ADB targeting and failure responses, automatic continuation after debugging approval, bounded/cancellable connection waits, text/binary APK manifests, bulk uninstall failure/cancellation handling, ownership-aware removal, reboot boundaries, explicit feature restoration, selective helper-file cleanup through real Windows PowerShell, fixed machine deployment paths, same-account UAC policy and protected runtime permissions.
- Desktop tests: three cases construct and render Setup, Android apps and Remove; verify deployment excludes adjacent unrelated executables/configuration; and verify worker-thread progress created before the application loop updates controls on the UI thread.
- Opt-in integration: downloaded the exact pinned WSA and platform-tools artifacts, verified both SHA-256 hashes, extracted the real archives through the production extractor, checked WSA identity/dependencies/settings entry point, and ran platform-tools 37.0.2 with a separate localhost ADB server. Passed; the server was stopped and extraction directories were cleaned.
- NuGet vulnerability lookup: no known vulnerable dependencies reported at validation time. This is not an independent security audit of WSA or the helper.
- PowerShell scripts: syntax parsed successfully.
- Distribution: Windows x64 self-contained single-file executables, ZIP and SHA-256 sidecar; downloaded WSA and platform-tools are excluded. Runtime and SharpCompress license notices are included.

The desktop visual pass adds coordinated light/dark palettes, Windows high-contrast colors, sidebar navigation, rounded controls, visible keyboard focus, selection counts, meaningful empty/search states, in-window progress/errors and expandable activity details. All three entry points share a code-drawn multi-resolution executable icon. The desktop rendering test now checks 28 combinations of page/state, theme and window size using an isolated state store with startup actions disabled. It verifies filtering, multi-selection and that bulk removal stays visible at the minimum window size. Long package IDs use one-line ellipsis with the full ID in a tooltip. Rendered previews were inspected directly. A live native click-through of this visual revision could not be completed because the previously available `orca` executable is no longer on PATH; packaged executable startup checks are separate from live GUI acceptance.

On the latest debugging follow-up, the WSA endpoint refused connections again; no real APK operation ran. An attached physical Android device was not targeted. Signed APK fixtures remain for the pending WSA-only acceptance test.

Existing-installation acceptance was run on the development PC after the user confirmed WSA is already installed: WSA 2407.40000.4.0, Windows build 26300, VMP enabled and no pending restart. The real setup/removal preservation test passed: only private helper tools were installed/removed, the existing WSA identity/location remained unchanged, and guards rejected any attempt to change Windows features or AppX registration.

The packaged setup interface was exercised on that existing subsystem. It completed setup without elevation, registered the exact quoted APK command, created all three Start menu shortcuts and wrote a journal recording that WSA/features were not owned. A packaged-UI crash in startup progress reporting was identified from the Windows .NET crash log and fixed by explicitly dispatching progress updates to WPF's owning dispatcher; the regression is covered by the desktop suite and the rebuilt packaged setup completed successfully. The task-owned crash dump was removed.

The packaged removal interface was also exercised against the existing subsystem. After confirmation, it removed the helper's ProgID/application registration, shortcuts and private platform-tools, then removed all 12 recorded helper files after the removal window closed. A task-owned file added to the app directory survived the uninstaller. The original Windows APK default choice and WSA registration remained unchanged. The added fixture was then cleaned up separately. The recovery journal remains by design. This validates removal of the helper alongside a pre-existing subsystem; it does not validate deletion of a freshly helper-owned WSA.

Real-APK acceptance is still incomplete. `127.0.0.1:58526` initially refused the connection; after the user authorized restarting only WSA, its debugging port responded but reported `unauthorized`. Developer mode was confirmed ON, and a stable test runner kept the connection alive for the full two-minute authorization deadline. It timed out before any APK install/uninstall. The bounded authorization-wait behavior has passing regression tests, including later approval, timeout and cancellation. No Android apps or debugging keys were changed. Signed disposable APKs and a dedicated loopback test server are retained for approval and the follow-up test. These observations are not a passing APK acceptance result.

**Not verified:** privileged feature changes, distinct-admin UAC, fresh WSA registration/boot, reboot/sign-in recovery, real APK installation/removal, Explorer associations and complete rollback on a disposable clean machine. These require the scenarios in [ACCEPTANCE.md](ACCEPTANCE.md). The development PC contains an existing user subsystem, so destructive fresh-install/rollback checks need a separate environment. No WSA installation or Windows feature/policy change was performed here.

The inspected WSA manifest declares a LocalSystem packaged service. Fresh registration now runs in a dedicated elevated worker, following Microsoft's packaged-service deployment requirements. The worker stages under Program Files, rechecks the pinned archive after copying it into protected storage, verifies ownership and ACLs, refuses conflicting WSA packages across accounts, and records a protected recovery journal. Removal requires that journal, the original caller SID and no remaining package registration at that location. Separate administrator credentials and Administrator protection configurations that change the elevated SID are deliberately rejected; fresh deployment currently requires same-account administrator consent. Regression tests cover the account/path/ACL policy, but actual privileged staging, service registration, boot, interrupted deployment and owned removal still need a disposable Windows environment. No privileged fresh-registration experiment was performed against the user's existing WSA.
