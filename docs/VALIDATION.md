# Validation record — 0.1.0 candidate

Recorded November 6, 2026 on Windows x64 using .NET SDK 10.0.203.

- Release build: succeeds with warnings treated as errors.
- Core regression suite: 43 cases cover download integrity and cache replacement, malformed/traversing/link archives, journal recovery, package/endpoint validation, ADB targeting and failure responses, text/binary APK manifests, bulk uninstall failure/cancellation handling, ownership-aware removal, reboot boundaries, explicit feature restoration, and selective helper-file cleanup through real Windows PowerShell.
- Desktop tests: three cases construct and render Setup, Android apps and Remove; verify deployment excludes adjacent unrelated executables/configuration; and verify worker-thread progress created before the application loop updates controls on the UI thread.
- Opt-in integration: downloaded the exact pinned WSA and platform-tools artifacts, verified both SHA-256 hashes, extracted the real archives through the production extractor, checked WSA identity/dependencies/settings entry point, and ran platform-tools 37.0.2 with a separate localhost ADB server. Passed; the server was stopped and extraction directories were cleaned.
- NuGet vulnerability lookup: no known vulnerable dependencies reported at validation time. This is not an independent security audit of WSA or the helper.
- PowerShell scripts: syntax parsed successfully.
- Distribution: Windows x64 self-contained single-file executables, ZIP and SHA-256 sidecar; downloaded WSA and platform-tools are excluded. Runtime and SharpCompress license notices are included.

Existing-installation acceptance was run on the development PC after the user confirmed WSA is already installed: WSA 2407.40000.4.0, Windows build 26300, VMP enabled and no pending restart. The real setup/removal preservation test passed: only private helper tools were installed/removed, the existing WSA identity/location remained unchanged, and guards rejected any attempt to change Windows features or AppX registration.

The packaged setup interface was exercised on that existing subsystem. It completed setup without elevation, registered the exact quoted APK command, created all three Start menu shortcuts and wrote a journal recording that WSA/features were not owned. A packaged-UI crash in startup progress reporting was identified from the Windows .NET crash log and fixed by explicitly dispatching progress updates to WPF's owning dispatcher; the regression is covered by the desktop suite and the rebuilt packaged setup completed successfully. The task-owned crash dump was removed.

The separate real-APK test could not reach Android: `127.0.0.1:58526` refused the connection before any APK installation. WSA's Windows settings were inspected directly and showed Developer mode ON at that address. The mode was refreshed OFF/ON and visually confirmed ON again; the debugger still refused connections. No test APK or existing Android app was installed or removed, and the test's private tools/server were cleaned up. Restarting WSA requires user approval because it closes open Android apps. Signed disposable fixture APKs are prepared for that follow-up test. These runtime observations are not a passing APK acceptance result.

**Not verified:** privileged feature changes, distinct-admin UAC, fresh WSA registration/boot, reboot/sign-in recovery, real APK installation/removal, Explorer associations and complete rollback on a disposable clean machine. These require the scenarios in [ACCEPTANCE.md](ACCEPTANCE.md). The development PC contains an existing user subsystem, so destructive fresh-install/rollback checks need a separate environment. No WSA installation or Windows feature/policy change was performed here.

Keep the GitHub binary release as a draft until the clean-machine checklist is complete. The public source repository and local candidate package are available for review. The helper is unsigned; production distribution needs a maintainer decision about signing and update/support policy.
